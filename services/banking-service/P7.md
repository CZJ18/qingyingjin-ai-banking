## 范围和架构

保留 Go + Gin + GORM 金融业务、整数分金额、双分录、归属校验、具体意向授权、执行幂等与审计。只增加 PostgreSQL 驱动、等价 schema、操作员快照迁移和数据库写围栏；没有重写资金执行器，也没有修改 Coze 原生 Agent/Workflow 引擎。

- `qingrongjin_finance`：独立金融核心数据库，不能与产品投影库混用。
- `qingrongjin_agent`：保留现有 FastAPI 产品投影和 LangGraph 状态，不迁移、不清空。
- Coze 原数据库：不迁移。
- MySQL 原金融库：切换后保留并冻结，作为对账与受控回退来源。

采用维护窗口内的单写入源：冻结源 → 一致快照导入 → 逐表及金融约束对账 → 激活目标 → 切换唯一 Go 服务 → 验收。没有在线 CDC、双写、自动数据库回退。

## 主库切换操作手册

以下为首次迁移时的操作顺序，实际主库切换证据见上表。当前主 PG 已承接业务增量，**不能把这组首次迁移或零增量回退命令直接重新运行**。再次迁移应准备独立目标，并遵循状态和快照门槛。开始前保证输出目录存在、无另一位操作员并行切换，并保留当前已验证的镜像及 MySQL 私有源配置。

1. 运行上面的配置和权限检查，确认产品 PG 原卷/网络保留。用新构建的迁移器验证两端 001–011，不得修改已应用 SQL 的 checksum。PG 目标保持空业务库 `standby`；只允许 CLI 显式替换完全未修改的 6 条 baseline 风险规则。
2. 建立维护窗口。金融确认请求在窗口内可能返回 503，执行结果不确定时先查原意向和幂等记录。冻结 MySQL 会排空数据库内已有写事务；旧 Go 进程和 worker 随后同样受数据库围栏限制。
3. 导入并生成完整聚合报告；失败保持冻结，检查原因，不自动解冻、删表或重新创建源数据。
4. 源保持 `frozen`，目标保持 `standby`，再次 compare。只有 46 表内容及双方 17 项不变量完全通过，才执行目标激活。
5. 使用 P7 镜像和 PG overlay 启动唯一 Banking Service；验证 app 身份、schema、readyz、产品 API、授权/执行、幂等及审计。重启后再次验证，不以镜像成功构建代替业务验收。
6. 保留 MySQL `frozen`、数据卷和所有报告。记录实际镜像摘要、两端状态/generation、对账 digest、账户/交易/意向行数、服务重启及产品结果。

```powershell
go run -buildvcs=false ./cmd/storage-control -mode freeze -env-file ../../deploy/banking/.env.local -output ../../output/p7/main-freeze.json

go run -buildvcs=false ./cmd/storage-migrate -mode verify -source-env ../../deploy/banking/.env.local -target-env ../../deploy/banking-postgres/finance.migrate.env.local -output ../../output/p7/main-verify.json

```

`storage-control` 的激活/回退会以 MySQL 命名锁协调，锁定 frozen peer，重新对账并以目标 generation 做比较后交换。普通 Agent、金融 Tool 和 REST 没有改变存储模式的接口。

## 回退规则

目标激活后**尚无任何业务增量**时：先冻结 PG，再比较 PG 与旧 MySQL 的完整快照；只有完全相同才允许 `rollback` 激活 MySQL。不能仅比较账户余额，也不能把预留序列或 `updated_at` 当成业务写计数。

```powershell
# 仅在完成上述零增量门槛后，从 services/banking-service 执行。
go run -buildvcs=false ./cmd/storage-control -mode freeze -env-file ../../deploy/banking-postgres/finance.migrate.env.local
go run -buildvcs=false ./cmd/storage-control -mode rollback -env-file ../../deploy/banking/.env.local -peer-env ../../deploy/banking-postgres/finance.migrate.env.local -output ../../output/p7/main-rollback.json
```

PG 已产生任意业务增量时，禁止恢复旧 MySQL 连接。必须冻结 PG，把完整快照反向导入**全新** MySQL schema，对账后切到新库；或继续保持冻结排查。迁移器不会覆盖旧库、删除增量或自动补偿资金。CLI 导入成功但输出文件写入失败时，数据库可能已经提交，应先查询状态和重新 verify，不要假设“命令非零退出即没有导入”。

## 已知限制及尚未满足项

- 本文完成范围为本机模拟金融系统的 P7 存储迁移与验收，不表示所有生产级需求或所有专业 Agent 的真实模型路径都完成验收。各项明确边界如下。
- 现有 MySQL 金融运行身份沿用历史 owner/DDL 能力，数据库围栏不能对抗拥有修改控制表或移除触发器权限的操作员。PG 使用独立非 owner app 角色收敛权限；MySQL 权限进一步拆分未在本阶段冒充完成。
- PG 基线以 ICU 非确定性 `qyj_mysql_ci` 尽量保留 MySQL 忽略大小写/重音的键比较。PG 17 对此类列直接使用 `LIKE` / 正则存在限制；现有商户筛选是精确匹配。新增模糊查询须明确比较语义并单独验收，不能假设所有 MySQL 排序/文本运算完全等价。
- 本机实际使用 PostgreSQL 17.6。迁移代码声明 PostgreSQL 14+ 且要求 ICU；其他主版本没有在本次逐版本实测。
- 本地 `sslmode=disable` 只用于 loopback / Docker 私有网络。生产 TLS、证书轮换、灾备恢复、HA 和在线升级没有完成生产验收。
- 在线 CDC、双写、无维护窗口迁移及旧库破坏性覆盖回退没有实现。迁移 CLI 是受信任操作员工具，不属于 Agent 自主权限。
- 每套完整核心集成的 6 个历史 Docker 测试跳过明确保留；Python 非显式集成回归另有 13 跳过、15 deselected，均没有计入通过。在线产品验证以本文链接的原始输出为准。
